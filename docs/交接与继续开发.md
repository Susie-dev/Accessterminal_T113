一、必须遵守的硬约束（改任何代码前先读这一节）
--------------------------------------------------------------------------------

这几条是重构的前提，**破坏它们等于把整个重构做废**：

1. **TCP 8887 信令语义逐字节兼容**
   - 终端 -> PC：`call`、`stopsend`、`unlock`
   - PC -> 终端：`accept`、`recstop`、`unlock`
   - 一律 UTF-8 文本行 + `'\n'` 结尾
   - `stopsend` **只在本地挂断时发**，远端发来 `recstop` 时**不发**
   - 注意 `"stop"` 是 `"stopsend"` 的前缀 —— 解析器必须缓冲突歧前缀，
     不要"看到 stop 就当成 Stop"

2. **UDP 报文格式与端口不可改**
   - `12345` 双向音频：裸 PCM，S16_LE / 16000 Hz / 单声道 /
     每包 320 帧（640 字节），**无包头**
   - `23456` 视频（PC 收）：每包一个**完整 JPEG**，`save(&buf, "JPEG", 75)`
     —— 注意是 **"JPEG"** 不是 "JPG"，这是 baseline 的不对称写法，**照抄**
     （音频那边用的是 "JPG"，两边故意不一致，别"顺手统一"）
   - `50000` 远程监看：PC 发裸 `"getframe"` / `"stop"`（**没有 `'\n'`**），
     终端收到 `getframe` 后才推流，50 ms 定时器（20 fps），
     `save(&buf, "JPEG")`（默认质量）
   - `23456` 与 `50000` 都**不做重组、不重传**

3. **音视频线程只在收到 `accept` 之后创建**
   - 唯一的例外（baseline 就这样，不要"修正"）：
     `CameraUdpServer`（UDP 50000）在 `Widget` 构造函数里就建，**不受 accept 门控**

4. **不迁移 Qt 版本**：目标就是 Qt5。T113 Tina SDK 常见 Qt 5.9~5.12，
   所以**不要用 Qt 5.15+ 才有的 API**（`errorOccurred`、`QStringView`、
   `QColorSpace`、`QRandomGenerator` 等），否则目标板编译不过。
   本项目虽然在本机用 Qt 5.15 编译，但代码刻意只用 5.9 就有的 API。

5. **C++11**，不是 C++14/17。禁用：`inline` 变量、结构化绑定、`if constexpr`、
   `std::optional`、`std::string_view`、`std::make_unique`、`std::filesystem`。
   （`constexpr auto` 可用；`auto` 与 range-for 可用。）

6. **`src/core/net/protocol.h` 与 `tests/test_protocol.cpp` 是冻结文件**，
   两个仓库（门口机 / 室内机）必须保持**内容完全一致**：
       protocol.h         SHA256 = 98627727e1fbda3a54dcb27d84a6a49e33b775990508f4ea89d167d518005523
       test_protocol.cpp  SHA256 = d779bb06d41b73126d37ea6f0bd97f910f6201696c25c3befeea078ccce6d52d
   **绝对不要往 protocol.h 里加 `Q_DECLARE_METATYPE`**（详见表尾"待办"第 3 条）。
   改这两个文件前，先读 `tools/check_protocol_sync.py`。

7. **不要做全仓库 CRLF -> LF 的批量转换**。只规范化你实际改过的文件。
   所有新文件必须 **LF、无 BOM**（UTF-8 无 BOM）。

### 故障注入自检（本工程最有价值的东西）

`tools/verify_*.py` 里有 **40 个夹具**，每一个都会：
  1. 故意把**被测代码**改坏（"变异"）；
  2. 重新编译、重新跑测试；
  3. 断言"测试**必须**变红"。

如果一个变异没被抓到，说明**那个测试没有判别力**，等于没测。

> 数字更正（第 31 轮）：原写"26 个"，实际在交接时已是 36 个。第 31 轮新增
> `tools/verify_checksum_dedup_rule.py`，共 37 个。它与其余夹具不同，是
> **跨平台的纯 Python 静态**故障注入（直接在合成仓库上调用规则函数，
> 不需要编译器），因此能在 Linux/CI 上跑 —— 其余多数夹具依赖 msys64 与
> Windows 路径（本机之外跑不了，见下文"三条铁律"）。

> 数字更正（第 40 轮）：新增三个夹具，共 **40 个**。三个都是**跨平台纯
> Python**（仓库根由 `__file__` 推导、解释器用 `sys.executable`，不依赖
> msys64 与 Windows 路径），因此在 Linux/CI 上直接可跑：
>   - `verify_qt5_invoke_method_rule.py` —— [qt5] 规则中"invokeMethod 的
>     functor 重载（Qt 5.10+）"那一条的自检；
>   - `verify_actuator_separation_rule.py` —— [actuator] 规则（开锁唯一出口、
>     执行器不掺补光）的自检；
>   - `verify_door_actuator_test.py` —— 新测试目标 `t113_door_actuator` 的
>     判别力自检：把"不假装开门 / 不重复驱动 / 不阻塞"三条约束分别改坏，
>     要求测试**变红**（实测 3/3 变红、对照保持绿）。
> 上文各处"37 个""18 个目标"是那几次运行的历史数字，**保留不改**。

**每写一条新的静态规则、每写一个新的测试，都必须配一个这样的夹具。**
这条纪律在本项目里已经连续 22 轮抓到真实缺陷（包括"测试自己写错了"）。
详见 README 开发约定第 33 / 50 条。

**跑这些夹具时的铁律**（都是血泪换来的，README 第 61/67/74/75/76/77/78 条）：

  0. **所有"就地改写仓库源文件"的夹具，现在统一用
     `tools/fixture_pristine.PristineGuard`。**（第 41 轮完成迁移：
     原先 5 个各抄一份，另有 10 个**只靠 `finally`**、还有 1 个
     **完全没有锁**。）它提供：磁盘原始副本 + 中断哨兵 + **新鲜度校验**
     + atexit/信号还原 + 同一进程内**可重入**的仓库级文件锁
     （`fi37_rewrite.lock`，目录用 `TEMP` 或系统临时目录，跨平台）。
     拿不到锁就立刻退出并说明，不会污染源码。

     第 42 轮补两条硬性检查（都是**实测出来的**真实缺陷，不是理论担忧）：

     - **锁名必须只有一把。** 审计所有 (锁名, 被改写文件集) 组合时发现
       `verify_credential_rule.py` 与 `verify_credential_store_test.py`
       **都改写 `credential_store.{h,cpp}` 却用了不同的锁名**。实测：在
       `fi37_rewrite.lock` 被占的情况下跑后者，它 **rc=0 正常跑完**并改写了
       同一批文件 —— 即文档里写的"共用一把文件锁"当时**并未真正成立**。
       现已统一为 `fi37_rewrite.lock`（16 个夹具一把锁）。
       **新增夹具时，锁名一律用 `fi37_rewrite.lock`。**
     - **"锁忙"退出码统一为 3**（2 保留给"夹具自身错误/锚点失效/基线红"）。
       此前 4 个返回 2、7 个返回 3 混用，调用方无法区分"因并发没跑"和
       "跑了且真失败" —— 而把并发跳过误当假绿是最危险的失败模式。

     **改动这套机制后必须跑 `python3 tools/verify_fixture_pristine.py`**
     （26 项）—— 它守的是"仓库源文件不会被静默回滚"，它自己错了
     受害的是源码本身，不是某个规则。

  1. **一次只跑一个**。两个会改写源文件的夹具并行，会互相污染 ——
      已经发生过：规则夹具报"没抓到"、行为夹具报莫名其妙误报，
      而单独串行重跑全部正常。共用文件锁会互相排斥，但你手动跑别的
      夹具时仍要注意（锁只挡得住**认同一把锁**的脚本 —— 所以第 0 条
      才要求锁名只有一把）。
  2. **不要在夹具扫描期间跑 `verify.py`**。它会在源文件被变异的瞬间读到
      中间状态，报出假的 `[dead-signal]` 之类告警。
  3. **尽量不要 `kill` 一个正在改写源文件的夹具**。它们现在有磁盘原始副本 +
      新鲜度校验 + 信号处理器，正常情况下能自愈。第 41 轮**实测**过这条底线：
      在一次全量扫描中途 `job_kill`，仓库里**零源文件被污染**，
      且没有残留锁或哨兵（升级确实有效）。但别故意去试探。
      （第 36 轮没有这些保障时真的留下过"看起来完全正常、只是少了一行"
      的源文件，直到下次运行才暴露。）
  4. **不要在夹具运行期间构建、跑测试或跑 `verify.py`**。夹具是"原地改写 →
      还原"，构建会在那一瞬间把**变异后的源码**编进目标文件。第 40 轮实测：
      一边跑 `verify_door_actuator_test.py`、一边后台 `cmake --build && ctest`，
      结果 `t113_door_actuator` 与 `t113_access_controller` 双双 Failed；
      源码还原后**串行重跑 20/20 全过**。判据：任何**读源码**的操作都要等夹具
      跑完（构建、ctest、verify.py、check_signatures.py 都算）。
  5. **夹具全红时，先怀疑夹具底座，再怀疑被测代码。** 第 41 轮两次真实教训：
     `verify.py` 的剥离器顺序错了让**全部 50 条规则**一起误报；
     `os.kill(pid,0)` 在 Windows 上不是存活探测，让陈旧锁永远无法接管、
     所有夹具静默停摆。两者都表现为"莫名其妙全红"。
     底座自检：`python3 tools/verify_stripper_robustness.py`（20 项）。
  6. **夹具的锚点和期望值会随被它盯着的代码一起过期**（README 第 76 条）。
     第 41 轮又抓到两起，都**不是**本轮引入的、且都藏了很久：
     `verify_form_call_rule.py` 的安全阀锚点在第 37 轮影子头加第三个宏时
     就失效了；`verify_dead_slot.py` 期望"变异后剩 2 条"是第 23 轮有 3 个
     不可达槽时的算术，基线降到 1 条后那个值**永远不可能满足** → 恒定假红。
     特点：**锚点失效会吵（报错退出），期望值失效会安静地恒定报红**。
     所以凡是"变异后数量应当变化"的断言，都必须**另有一条把基线钉成
     精确值**的用例 —— 只写下界（`>=1`）等于放弃对基线的监控。
     **改动被某个夹具盯着的代码时，顺手跑一遍那个夹具。**
  7. **"从不执行的错误处理路径"是 bug 的温床 —— 要么修，要么删。**
     第 42 轮实测：4 个夹具在**锁忙**时抛 `NameError: name 'LOCK' is not
     defined`（第 41 轮迁移到 `PristineGuard` 时忘了删文案里的 `% LOCK`）。
     它只在锁被别的进程占用时才执行，平时**从不触发**，所以 43/43 全绿
     也照样带着它。发作时恰是用户最需要清晰提示的时刻，却只看到 Python
     回溯。**判据**：如果一个分支你无法用一次真实运行触发它，那它既没被
     测过、也没被读过 —— 它坏了你永远不会知道。
     顺带删掉了 `verify_door_actuator_test.py` 里因同一原因变成死代码的
     `LOCK`/`_acquire_lock`/`_release_lock` 三个符号。
     同源教训：**"看着像多一道防线、其实永远不会触发"的代码比没有更糟**，
     因为它会让人误以为那里已经被保护了。
  8. **静态规则的"作用域"是它判别力的核心，必须专门证明一次。**
     第 42 轮新增的 `[latest-value]` 规则检查"每个 `QtConcurrent::run` 提交点
     所在函数有没有背压闸门"。如果写成**文件级**（这个文件里有没有闸门），
     那么"在已有闸门的文件里新增一个无闸门提交点"会**假绿** —— 而真实项目
     就是这样一点点长出无界任务堆积的。做法：夹具里专门有一个变异钉住这点，
     并且**实测把规则临时改成文件级后它确实漏报**（红 → 绿），改回函数级又
     变红。没有这一步，那条变异可能只是因为别的原因变红，证明不了什么。
     凡是规则涉及"在某个范围内查找"的地方（函数体、语句块、临界区），
     都该问一句：**范围放宽到上一层，我的变异还能被抓到吗？**
  9. **检查者本身也要被检查**（README 第 78 条）。`verify.py` 出问题时症状
     往往**不是报错，而是安静地少跑一条规则** —— `rc=0`、"全部检查通过"，
     一切正常。第 42 轮实测到三种形态：①定义了 `check_*` 却忘了在 `main()`
     注册（该规则从不执行）；②错误处理路径从不触发（4 个夹具的
     `% LOCK` `NameError`，只在锁忙时炸）；③文档里手写的"50 项检查"

### 【P4】人脸门禁阈值的上限形同虚设 —— 已修（第 38 轮）

**更正**：原文写"`behavior.face_confidence_threshold` **没有做范围夹取**"，
这是**错的**。真实的夹取在 `app_config.h` 的访问器里。

第 29 轮的规则只搜了 `app_config.cpp` 里的 `qBound|clamp` 子串，而夹取根本
不在那个文件里（数值访问器统一在 `.h` 出口兜底），于是**误报**成"没有任何
范围约束"。第 31 轮改为解析头文件里的真实上下限。

**真实问题**：夹取存在，但原上限 `1e9` 大到形同虚设。下限 0.0 有效
（挡住负数），上限等于没设。而探针已证实：**门禁安全完全取决于这个值**
（LBPH 单 label 时 `predictedLabel == 1` 恒为真，唯一判据就是这个阈值）。

**第 31 轮把判据定成了 `1e6`，这是第二个错**：`1000` 这种同样致命的写法
被判为合格。第 38 轮用探针量了 LBPH 的真实距离，才拿到正确的门槛：

| 对象 | 实测距离（LBPH `create()` 默认参数，8x8 网格） |
| --- | --- |
| 同一身份（含噪声/光照抖动） | 0 ~ ~103 |
| 完全不同的图像（冒充者） | ~170 ~ ~256 |
| 随机噪声 | 饱和于 ~256 |

距离在 **~256 处饱和**，因此阈值 `>= 256` 时任何图像（含完全陌生的脸）都判
"通过"：`1e9`、`1000`、`256` 在安全意义上完全等价。

**已取方案**：上限由 `1e9` 收到 **`150.0`**，它落在"本人 <= ~103"与
"冒充者 >= ~170"之间。默认值 `90` 仍在区间内，故**未配置时行为逐字节不变**；
只有把阈值配到 `150` 以上（含 `900` / `1e9`）才被夹到 `150` —— 这是一次
**有意的行为变化**（第 38 轮独立决定）。

配套：
  - `tools/verify.py` 的 face-gate 由**告警**升级为**失败**：上限 `>= 256`
    即红，判据与度量挂钩（不再用凭感觉的 `1e6`）。
  - `tools/verify_face_gate_rule.py` 给出两侧边界：`256.0` 必须红、
    `255.0` 必须通过；夹具同时改为从脚本位置推仓库根（原先写死 Windows
    路径），使这条规则在 Linux/CI 上可验证。
  - `tests/test_app_config.cpp` 把 `150.0` 钉死（`900` / `1e9` 一律夹到 `150`，
    而 `90` / `77.5` / `120.5` 原样通过）。
  - `tests/test_face_manager.cpp` 从**行为**侧再钉一遍：阈值推到上限 `150`
    时，完全不同的图像仍必须被拒绝。

**仍然存在的限制**：`150` 是由**合成图案**的探针定的，不是现场人脸标定。
现场若发现需要更松/更紧的阈值，应连带更新本表与规则门槛，而不是随手改常数。

四、最近几轮做了什么（第 37 ~ 39 轮）
--------------------------------------------------------------------------------

**目标**：`src/ui/form_finger.cpp`（347 行）——**现场真正执行**的指纹注册
状态机。注意指纹注册在本工程里有**两份**实现：
  - A) `FingerprintManager::startEnroll(int)`：有测试、**零生产调用者**
  - B) `Form_finger::startFingerRegisterStep()` + `doFingerCollect()`：
    **这才是现场跑的那条**（P1 里说的就是这个）

**发现的缺陷（真实、已修）**：`Form_finger` 析构时对**已被销毁**的
`FingerprintManager` 调用 `setSuspended(false)`。

原因：两者都是 `Widget` 的子对象，而 **Qt 按创建顺序销毁子对象
（先建先死，不是逆序）**。生产代码里管理器在 `widget.cpp:250` 创建、
窗体在 `widget.cpp:670` 创建，所以 `delete Widget` 时管理器**先死**，
窗体析构时那个**裸指针仍然非空**（`if` 判空挡不住已经死掉的对象）。

**触发条件**：用户进过指纹注册、且**没有**点『退出』就关机
（点『退出』会把句柄清空，因而不触发 —— 所以这条路径很容易漏测，
手工测试几乎总会先点『退出』）。

**修法**：成员类型改为 `QPointer<FingerprintManager>`（被指对象销毁后
自动变空）。与 `widget.h` 里 `m_passwdForm` 用 `QPointer` 同理。

**与 baseline 的关系**：baseline 的 `form_finger.cpp` 里**完全没有**
`suspend` / `setSuspended` / `FingerprintManager` 等字样（已逐项 grep 实测）。
整套"串口互斥 + 挂起恢复"设计是**重构引入**的，所以这条 UAF 是
**重构回归**，不是继承缺陷 —— 修它**不违反**行为兼容硬约束。

**本轮最值钱的一条教训**：**"它会不会崩"不能当作回归守卫。**
第一版回归测试就是"不点退出、直接让窗体析构，看它崩不崩"。
故障注入实测：针对当时**较薄的**测试文件，把 `QPointer` 改回裸指针后
**5/5 运行全部正常退出，一次都没崩**；补强测试后同一变异 **8/8 全部崩溃**。

原因是 use-after-free 属**未定义行为**：Qt 析构只是把内存还给分配器，
"刚释放、尚未被复用"的那块内存往往仍保存着原 vtable 与字段。
**崩不崩取决于后续代码是否恰好复用了那块内存 —— 是偶然的。**

所以本轮的处置是：
  1. 把"靠崩溃判定"**降级**，不作为唯一守卫；
  2. 新增**确定性**的静态规则
     `check_form_finger_suspended_manager_is_guarded`（in `tools/verify.py`），
     逐字钉住"成员必须是 `QPointer`、必须 `#include <QPointer>`、
     挂起/恢复必须成对且分别落在退出与析构两个函数体内"；
  3. 单元测试改钉**成因前提**（Qt 确实先销毁先创建的子对象），
     顺序一反就红（已用故障注入验证有判别力）。

**本轮新增的测试目标**：`t113_test_form_finger`（第 18 个）
  - 27 个用例，全部通过
  - 链接**真实** `FingerprintManager`（互斥语义在真实现里，不能用替身）
  - 只用链接期替身替换 `HailinFingerprint`（假串口设备）
  - 断言落在**整条线上字节序列**上：
    ```
    01 | 01 02 01 | 01 02 02 | 01 02 03 | 05 | 06 01 12 34
    超时 500 | 2000 2000 | 2000 2000 | 2000 2000 | 2000 | 2000
    ```

    （每一步其实有**两条** `GET_IMAGE`：一条来自"检测手指"轮询 500ms，
    一条来自 `doFingerCollect()` 再采集一次 2000ms —— 这是与 baseline

**本轮的两个故障注入夹具**：

### 第 41 轮：门禁口令从**明文比对**改为**加盐哈希**，以及"Release 绿 ≠ Debug 绿"

本轮把方案 P2 的存储层做完了，**新增/改动 4 个源文件 + 2 个测试目标 +
2 条静态规则 + 2 个故障注入夹具**。修复层面的要点：

  - **真缺陷 1（安全）**：`PasswordManager::checkPassword()` 原是
    `input == password` —— 明文比对；口令来自 `AppConfig`，配置里是明文
    `"5788"`。现在改为 `CredentialStore` 的加盐迭代 SHA-256 + **定长比较**。
    明文只在栈上活一瞬间，不进成员、不进文件、不进日志。
  - **真缺陷 2（安全，由**既有**规则抓到）**：我在新代码里直接用了
    `QByteArray::fromHex()`。它**不报错**，会跳过非法字符重新配对 ——
    被篡改的哈希串会"成功"解出**内容全错**的字节。本工程既有的
    `[hex-parse]` 规则当场把它抓了出来（`src/managers/credential_store.cpp`
    5 处）。修法是加 `isHexOnly()` 逐字符校验。
  - **真缺陷 3（可移植性）**：类内初始化的 `static const int` 被
    `qBound()` **ODR-使用**，C++11 要求类外定义。**Release（-O2）内联所以
    链接通过，`--coverage -O0` 不内联于是两个测试目标链接失败**。
    这条只有 Debug 构建才看得见 —— 见 README 开发约定第 72 条。
  - **修掉一条既有工具缺陷**：`tools/check_host_compile.sh` 的
    `-isystem $QTSP_INC` 在 `qmake` 缺失时退化成裸 `/mingw64/include`，
    **遮蔽 libstdc++**（`#include_next <stdlib.h>` 找不到），21 个文件全误报。
    修完 **21/21** 通过。

**故障注入抓出 12 个问题，全部是我自己的错**（写规则/写测试/写变异时犯的），
无一例外都是"以为验证了、其实没验证"：

| 对象 | 数量 | 典型 |
|---|---|---|
| 我的新静态规则 | 6 处假绿 | `"add_test(...)"` 子串在**注释行**里也成立 —— 把那行注释掉，目标被摘出 ctest 而规则不响 |
| 我的新行为夹具 | 2 处 | 变异写错（"不累加"写成"加倍"）；对照 `old == new` 被自己的守卫拦下 |
| 我的新测试 | 4 处 | ①用 `hashSecret(plain, salt, n)` 观测 `setSecret()` —— 盐是测试自己传的，"内部改固定盐"照样绿；②"到期自动解锁"的清理逻辑**删掉也全绿**；③非法字符的构造被长度判据掩盖 |

**教训**：新写的安全测试**特别容易恒真**（大量"不包含 X"的否定断言）。
唯一可靠的办法是**对每条新规则、每个新测试都做故障注入**，并且
**阴性断言必须配阳性对照**。

### 这两轮共同的教训（比修复本身更重要）

上面两个缺陷，**48 项静态检查与 18 个单元测试目标都没有发现**，因为它们都只
覆盖"正常路径"：

  - P4 需要**量真实数值**才能发现"门槛定错了"—— 原来的规则只问"有没有 clamp"，
    不问"clamp 的上限是不是真的安全"；
  - 第 39 轮需要**真的把可执行文件跑起来**才能看到日志洪泛 —— 单元测试里的

配置。**凡是要下"能编译/能链接"的结论，都必须说清是在哪种配置下得到的。**

所以：**"本机 18/18 全绿"不等于没问题**。上板冒烟（P0）不可替代；
遇到数值/阈值类问题时，"先做探针、再写断言"应当成为默认动作；
遇到"安全性质"时，"先做故障注入、再相信测试"应当成为默认动作。

  Linux 上要跑起**完整**验证，有两处环境缺口需要 workaround（都是缺 dev 包，
  与代码无关）：

  1. **`Qt5SerialPort` 只有运行库、没有 dev 包** → CMake 报
     `Could not find a package configuration file provided by "Qt5SerialPort"`。
     临时取 dev 包解出来，再把 `.so` 指向系统真实库：
     ```sh
     apt-get download libqt5serialport5-dev
     dpkg-deb -x libqt5serialport5-dev_*.deb /tmp/qtsp
     ln -sf /usr/lib/x86_64-linux-gnu/libQt5SerialPort.so.5.15.3 \
            /tmp/qtsp/usr/lib/x86_64-linux-gnu/
     cmake -S tests -B build -G Ninja \
       -DQt5SerialPort_DIR=/tmp/qtsp/usr/lib/x86_64-linux-gnu/cmake/Qt5SerialPort
     ```
  2. **`tools/devstubs/sys/socket.h` 直接 `#include <_mingw.h>`**，
     在 Linux 上编译 `t113_test_audio_manager` 会
     `fatal error: _mingw.h: No such file or directory`。
     第 39 轮是在**副本**里打补丁后构建的（未改仓库）：把该 include 用
     `#ifdef __MINGW32__` 包住、`socklen_t` 在 `__linux__` 下取
     `unsigned int`、并把 `sendto/recvfrom` 的 `int addrlen` 改成 `socklen_t`。
     **第 40 轮已在仓库里修掉**（提交 `devstubs: 让主机端检查在 Linux 上可用`），
     修完后 Linux 上 `cmake -S tests` → 构建 → `ctest` **18/18 通过
     （110.32s）**，不再需要打副本补丁。
     MinGW 分支保持原样（`_mingw.h` 仍只在 `__MINGW32__` 下包含、
     `socklen_t` 仍为 `int`），因此 Windows 侧行为不变。

     注：上面第 1 条里 `apt-get download` 解出来的 dev 包，除了
     `Qt5SerialPort_DIR`，还需要**版本化库名**的软链才认（CMake 找的是
     `libQt5SerialPort.so.5.15.3`，dev 包里只有 `.so`）：
     ```sh
     ln -sf /usr/lib/x86_64-linux-gnu/libQt5SerialPort.so.5.15.3 \
            /tmp/qtsp/usr/lib/x86_64-linux-gnu/libQt5SerialPort.so.5.15.3
     ```

  构建**应用**（不只是测试）时，主工程还需要显式给 libgpiod 路径：
  ```sh
  cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
    -DGPIO_INCLUDE_DIR=/usr/include \
    -DGPIO_LIBRARY=/usr/lib/x86_64-linux-gnu/libgpiod.so
  ```

### 容易踩的坑（都踩过了）

  - **根目录 `CMakeLists.txt` 需要 ALSA，本机配不了。**
    要构建一律进 `tests/`。这是刻意的设计，不是缺陷。
  - **`verify.py` 的输出重定向到文件后是 UTF-16LE**（PowerShell 干的），
    读的时候要用 `.decode('utf-16-le', errors='replace')`。
  - **覆盖率报告是 GBK**。重定向到文件再读。
  - **探针程序必须只输出 ASCII**。中文经 PowerShell 捕获会变乱码。
  - **Windows 上写探针要用 `qDebug()` 并重定向到文件**，
    不要指望嵌套 pwsh -> bash 的流捕获。
  - **Widgets 测试需要 `QT_QPA_PLATFORM=offscreen`**。
    `QFontDatabase: Cannot find font directory` 与
    `Could not create pixmap from :\pics\calloff.png` 都是**良性**警告。
  - **不要用 `grep` / `tail` 的 pwsh 原生版本**（PATH 里没有）。
    要过滤就在 bash 里做。
  - `git` 不在新 pwsh 的 PATH 里，用绝对路径。

--------------------------------------------------------------------------------
六、什么样的改动才算"做完了"
--------------------------------------------------------------------------------

沿用本项目已经形成的标准（README 开发约定）：

  1. **断言必须落在"输出"上**：线上字节、ALSA/GPIO 句柄、发出的信号、
     走了哪个日志分支。—— "有测试"不等于"被测到"。
  2. **新测试必须配故障注入**，并且证明"把被测代码改坏它就会红"。
     在缺陷代码上不失败的测试**没有价值**。
  3. **行为不可观测的防御性代码，也要有静态规则守**，并在夹具里
     如实记入 `UNDETECTABLE` **并写明原因** —— 没有守卫的死角要看得见。
  4. **报覆盖率必须连分母一起报**，并把未覆盖行分成"不可达 / 可达未测"。
  5. **"X 不出现"的断言必须配阳性对照**，否则捕获管道坏了它照样通过。
  6. **机制必须用真实实现，别复制一份进替身**（除非确实链接不进来，
     且要在注释里说明那是副本、由哪条静态规则守）。
