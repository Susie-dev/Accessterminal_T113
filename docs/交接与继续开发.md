一、必须遵守的硬约束（改任何代码前先读这一节）
--------------------------------------------------------------------------------

这几条是重构的前提，**破坏它们等于把整个重构做废**：

1. **TCP 8887 信令语义逐字节兼容**
   - 终端 -> PC：`call`、`stopsend`、`unlock`
   - PC -> 终端：`accept`、`recstop`、`unlock`
   - 一律 UTF-8 文本行 + `'\n'` 结尾
   - `stopsend` **只在本地挂断时发**，远端发来 `recstop` 时**不发**
   - 注意 `"stop"` 是 `"stopsend"` 的前缀 —— 解析器必须缓冲突歧前缀，
     不要"看到 stop 就当成 Stop"

2. **UDP 报文格式与端口不可改**
   - `12345` 双向音频：裸 PCM，S16_LE / 16000 Hz / 单声道 /
     每包 320 帧（640 字节），**无包头**
   - `23456` 视频（PC 收）：每包一个**完整 JPEG**，`save(&buf, "JPEG", 75)`
     —— 注意是 **"JPEG"** 不是 "JPG"，这是 baseline 的不对称写法，**照抄**
     （音频那边用的是 "JPG"，两边故意不一致，别"顺手统一"）
   - `50000` 远程监看：PC 发裸 `"getframe"` / `"stop"`（**没有 `'\n'`**），
     终端收到 `getframe` 后才推流，50 ms 定时器（20 fps），
     `save(&buf, "JPEG")`（默认质量）
   - `23456` 与 `50000` 都**不做重组、不重传**

3. **音视频线程只在收到 `accept` 之后创建**
   - 唯一的例外（baseline 就这样，不要"修正"）：
     `CameraUdpServer`（UDP 50000）在 `Widget` 构造函数里就建，**不受 accept 门控**

4. **不迁移 Qt 版本**：目标就是 Qt5。T113 Tina SDK 常见 Qt 5.9~5.12，
   所以**不要用 Qt 5.15+ 才有的 API**（`errorOccurred`、`QStringView`、
   `QColorSpace`、`QRandomGenerator` 等），否则目标板编译不过。
   本项目虽然在本机用 Qt 5.15 编译，但代码刻意只用 5.9 就有的 API。

5. **C++11**，不是 C++14/17。禁用：`inline` 变量、结构化绑定、`if constexpr`、
   `std::optional`、`std::string_view`、`std::make_unique`、`std::filesystem`。
   （`constexpr auto` 可用；`auto` 与 range-for 可用。）

6. **`src/core/net/protocol.h` 与 `tests/test_protocol.cpp` 是冻结文件**，
   两个仓库（门口机 / 室内机）必须保持**内容完全一致**：
       protocol.h         SHA256 = 98627727e1fbda3a54dcb27d84a6a49e33b775990508f4ea89d167d518005523
       test_protocol.cpp  SHA256 = d779bb06d41b73126d37ea6f0bd97f910f6201696c25c3befeea078ccce6d52d
   **绝对不要往 protocol.h 里加 `Q_DECLARE_METATYPE`**（详见表尾"待办"第 3 条）。
   改这两个文件前，先读 `tools/check_protocol_sync.py`。

7. **不要做全仓库 CRLF -> LF 的批量转换**。只规范化你实际改过的文件。
   所有新文件必须 **LF、无 BOM**（UTF-8 无 BOM）。

### 故障注入自检（本工程最有价值的东西）

`tools/verify_*.py` 里有 **37 个夹具**，每一个都会：
  1. 故意把**被测代码**改坏（"变异"）；
  2. 重新编译、重新跑测试；
  3. 断言"测试**必须**变红"。

如果一个变异没被抓到，说明**那个测试没有判别力**，等于没测。

> 数字更正（第 31 轮）：原写"26 个"，实际在交接时已是 36 个。第 31 轮新增
> `tools/verify_checksum_dedup_rule.py`，共 37 个。它与其余夹具不同，是
> **跨平台的纯 Python 静态**故障注入（直接在合成仓库上调用规则函数，
> 不需要编译器），因此能在 Linux/CI 上跑 —— 其余多数夹具依赖 msys64 与
> Windows 路径（本机之外跑不了，见下文"三条铁律"）。

**每写一条新的静态规则、每写一个新的测试，都必须配一个这样的夹具。**
这条纪律在本项目里已经连续 22 轮抓到真实缺陷（包括"测试自己写错了"）。
详见 README 开发约定第 33 / 50 条。

**跑这些夹具时的三条铁律**（都是血泪换来的，README 第 61/67 条）：

  1. **一次只跑一个**。两个会改写源文件的夹具并行，会互相污染 ——
     已经发生过：规则夹具报"没抓到"、行为夹具报莫名其妙误报，
     而单独串行重跑全部正常。现在两个新夹具已经用**共用文件锁**互相排斥，
     但你手动跑别的夹具时仍要注意。
  2. **不要在夹具扫描期间跑 `verify.py`**。它会在源文件被变异的瞬间读到
     中间状态，报出假的 `[dead-signal]` 之类告警。
  3. **绝不要 `kill` 一个正在改写源文件的夹具**。现在它们有磁盘原始副本 +
     中断哨兵 + 信号处理器，正常情况下能自愈；但别去试探这条底线。
     （第 36 轮真的发生过：夹具被外部杀死、仓库里留下一个"看起来完全正常、
     只是少了一行"的源文件，直到下次运行才暴露。）

### 【P1】三个"不可达"的槽：接线还是删除？（需要产品决策）

`tools/verify.py` 报了 3 条 `[dead-slot]` 告警。它们的共同点：
**写了、有测试、但没有任何生产调用者**。也就是说：为它们写的测试覆盖的是
**平行实现**，不是现场路径；改它们不会影响现场行为。

  1. `FingerprintManager::startEnroll(int)`
     —— 真正跑的是 `Form_finger` 的内联状态机（已在本轮被完整测试覆盖）
  2. `Widget::onFingerprintEnroll()`
  3. `Widget::onFingerprintIdentify()`

**为什么没动手**：删代码 / 接线都会改变行为，属产品决策，不属于"重构"。
**你需要做的**：确认这三条是否还需要保留为公开 API。

  - 若**不需要** -> 删除它们**以及**为它们写的测试（否则测试在守一个
    永远不会被执行的平行实现，还会掩盖真正路径的缺陷）。
  - 若**需要**（比如打算将来接上）-> 在注释里写明"刻意保留的公开 API"，
    并按 README 的做法把它从告警里排除。
  - 若打算**接上** -> 注意 baseline 里 `addFingerRequested` 是声明在
    `public slots:` 而不是 `signals:`，所以 `connect` 会在**运行期**失败
    （打印 "signal not found"）并返回 false。这正是它在 baseline 里
    "看起来配好了、实际从未生效"的原因。要接必须先把它改成真信号。

### 【P2】死代码 `calcChecksum()` —— 已修（第 31 轮）

`HailinFingerprint::calcChecksum()` 原本**零调用者**，而 `buildPacket()` 里
内联了一段**一模一样**的校验和循环。baseline 同样如此（属继承缺陷）。

**原风险**：两份拷贝会各自漂移。已有故障注入实测：只改**死的那份**，
18 个指纹用例全部照常通过。

**已取方案**：让 `buildPacket()` 调用 `calcChecksum()`，消除重复。
行为不变（累加范围仍是自下标 6 起算），死代码同时消失。

配套改动：
  - `tests/fake_fingerprint_device.cpp` 同步为"调用辅助函数"，避免替身里
    又出现第二份循环；替身与生产的辅助函数体由
    `check_fake_fingerprint_builds_same_bytes` 逐操作比对。
  - `tools/verify.py` 的 `[dup-checksum]` 从**告警**升级为**断言**
    （循环 >= 2 次即 fail；只剩一份但零调用者也 fail）。
  - 故障注入 `tools/verify_fingerprint_wire_test.py` 里那条
    "（已知不可区分·死代码）"变异**变成了可区分**，已转成正常致命变异。

### 【P3】指纹应答的包标识没有校验（当前只告警，未修）

`tools/verify.py` 报 7 条 `[fp-ack-tag]` 告警。问题：
下面这些地方把 `resp[9]` 当作确认码，但**没有校验包标识 `resp[6] == 0x07`**：

    - `hal/fingerprint_hailin.cpp:620`  `stepIdentify()`
    - `managers/fingerprint_manager.cpp:81`   `startIdentify()`
    - `managers/fingerprint_manager.cpp:207`  `startEnroll()`
    - `ui/form_finger.cpp:123`  `startFingerRegisterStep()`
    - `ui/form_finger.cpp:195`  `doFingerCollect()`
    （同文件的 `autoIdentify()` 是**校验了的** —— 两条路径判据不一致）

**后果**：串口噪声或命令回显（`byte[9] == 0` 但标识不是应答）会被误判成
"手指已按下"，界面直接进入采集步骤。

**为什么没修**：收紧判据会**改变现场行为**，硬约束要求行为兼容。
**决策者需要知道**：这是一条真实存在的偏差（不是理论风险），

### 【P4】人脸门禁阈值的上限形同虚设 —— 已修（第 38 轮）

**更正**：原文写"`behavior.face_confidence_threshold` **没有做范围夹取**"，
这是**错的**。真实的夹取在 `app_config.h` 的访问器里。

第 29 轮的规则只搜了 `app_config.cpp` 里的 `qBound|clamp` 子串，而夹取根本
不在那个文件里（数值访问器统一在 `.h` 出口兜底），于是**误报**成"没有任何
范围约束"。第 31 轮改为解析头文件里的真实上下限。

**真实问题**：夹取存在，但原上限 `1e9` 大到形同虚设。下限 0.0 有效
（挡住负数），上限等于没设。而探针已证实：**门禁安全完全取决于这个值**
（LBPH 单 label 时 `predictedLabel == 1` 恒为真，唯一判据就是这个阈值）。

**第 31 轮把判据定成了 `1e6`，这是第二个错**：`1000` 这种同样致命的写法
被判为合格。第 38 轮用探针量了 LBPH 的真实距离，才拿到正确的门槛：

| 对象 | 实测距离（LBPH `create()` 默认参数，8x8 网格） |
| --- | --- |
| 同一身份（含噪声/光照抖动） | 0 ~ ~103 |
| 完全不同的图像（冒充者） | ~170 ~ ~256 |
| 随机噪声 | 饱和于 ~256 |

距离在 **~256 处饱和**，因此阈值 `>= 256` 时任何图像（含完全陌生的脸）都判
"通过"：`1e9`、`1000`、`256` 在安全意义上完全等价。

**已取方案**：上限由 `1e9` 收到 **`150.0`**，它落在"本人 <= ~103"与
"冒充者 >= ~170"之间。默认值 `90` 仍在区间内，故**未配置时行为逐字节不变**；
只有把阈值配到 `150` 以上（含 `900` / `1e9`）才被夹到 `150` —— 这是一次
**有意的行为变化**（第 38 轮独立决定）。

配套：
  - `tools/verify.py` 的 face-gate 由**告警**升级为**失败**：上限 `>= 256`
    即红，判据与度量挂钩（不再用凭感觉的 `1e6`）。
  - `tools/verify_face_gate_rule.py` 给出两侧边界：`256.0` 必须红、
    `255.0` 必须通过；夹具同时改为从脚本位置推仓库根（原先写死 Windows
    路径），使这条规则在 Linux/CI 上可验证。
  - `tests/test_app_config.cpp` 把 `150.0` 钉死（`900` / `1e9` 一律夹到 `150`，
    而 `90` / `77.5` / `120.5` 原样通过）。
  - `tests/test_face_manager.cpp` 从**行为**侧再钉一遍：阈值推到上限 `150`
    时，完全不同的图像仍必须被拒绝。

**仍然存在的限制**：`150` 是由**合成图案**的探针定的，不是现场人脸标定。
现场若发现需要更松/更紧的阈值，应连带更新本表与规则门槛，而不是随手改常数。
详见 README 开发约定第 70 条。

### 【P5】继承缺陷：密码窗体"退格一次删两位"

四、本轮（第 37 轮）做了什么 —— 一条真实的 use-after-free
--------------------------------------------------------------------------------

**目标**：`src/ui/form_finger.cpp`（347 行）——**现场真正执行**的指纹注册
状态机。注意指纹注册在本工程里有**两份**实现：
  - A) `FingerprintManager::startEnroll(int)`：有测试、**零生产调用者**
  - B) `Form_finger::startFingerRegisterStep()` + `doFingerCollect()`：
    **这才是现场跑的那条**（P1 里说的就是这个）

**发现的缺陷（真实、已修）**：`Form_finger` 析构时对**已被销毁**的
`FingerprintManager` 调用 `setSuspended(false)`。

原因：两者都是 `Widget` 的子对象，而 **Qt 按创建顺序销毁子对象
（先建先死，不是逆序）**。生产代码里管理器在 `widget.cpp:250` 创建、
窗体在 `widget.cpp:670` 创建，所以 `delete Widget` 时管理器**先死**，
窗体析构时那个**裸指针仍然非空**（`if` 判空挡不住已经死掉的对象）。

**触发条件**：用户进过指纹注册、且**没有**点『退出』就关机
（点『退出』会把句柄清空，因而不触发 —— 所以这条路径很容易漏测，
手工测试几乎总会先点『退出』）。

**修法**：成员类型改为 `QPointer<FingerprintManager>`（被指对象销毁后
自动变空）。与 `widget.h` 里 `m_passwdForm` 用 `QPointer` 同理。

**与 baseline 的关系**：baseline 的 `form_finger.cpp` 里**完全没有**
`suspend` / `setSuspended` / `FingerprintManager` 等字样（已逐项 grep 实测）。
整套"串口互斥 + 挂起恢复"设计是**重构引入**的，所以这条 UAF 是
**重构回归**，不是继承缺陷 —— 修它**不违反**行为兼容硬约束。

**本轮最值钱的一条教训**：**"它会不会崩"不能当作回归守卫。**
第一版回归测试就是"不点退出、直接让窗体析构，看它崩不崩"。
故障注入实测：针对当时**较薄的**测试文件，把 `QPointer` 改回裸指针后
**5/5 运行全部正常退出，一次都没崩**；补强测试后同一变异 **8/8 全部崩溃**。

原因是 use-after-free 属**未定义行为**：Qt 析构只是把内存还给分配器，
"刚释放、尚未被复用"的那块内存往往仍保存着原 vtable 与字段。
**崩不崩取决于后续代码是否恰好复用了那块内存 —— 是偶然的。**

所以本轮的处置是：
  1. 把"靠崩溃判定"**降级**，不作为唯一守卫；
  2. 新增**确定性**的静态规则
     `check_form_finger_suspended_manager_is_guarded`（in `tools/verify.py`），
     逐字钉住"成员必须是 `QPointer`、必须 `#include <QPointer>`、
     挂起/恢复必须成对且分别落在退出与析构两个函数体内"；
  3. 单元测试改钉**成因前提**（Qt 确实先销毁先创建的子对象），
     顺序一反就红（已用故障注入验证有判别力）。

**本轮新增的测试目标**：`t113_test_form_finger`（第 18 个）
  - 27 个用例，全部通过
  - 链接**真实** `FingerprintManager`（互斥语义在真实现里，不能用替身）
  - 只用链接期替身替换 `HailinFingerprint`（假串口设备）
  - 断言落在**整条线上字节序列**上：
    ```
    01 | 01 02 01 | 01 02 02 | 01 02 03 | 05 | 06 01 12 34
    超时 500 | 2000 2000 | 2000 2000 | 2000 2000 | 2000 | 2000
    ```
    （每一步其实有**两条** `GET_IMAGE`：一条来自"检测手指"轮询 500ms，
    一条来自 `doFingerCollect()` 再采集一次 2000ms —— 这是与 baseline
    一致的既有行为，**不是**重复下发）

**本轮的两个故障注入夹具**：
  - `tools/verify_form_finger_test.py`：23 个变异全部抓到，
    1 个"行为上不可观测"的变异按预期抓不到，2 个对照不误报
  - `tools/verify_form_finger_rule.py`：13 个变异全部抓到，3 个对照不误报

**本轮还修了工具自身的两个缺陷**（这才是重点）：
  1. **夹具的自愈逻辑会静默回滚我自己的合法修改**。
     第一版判据是"磁盘副本 != 当前文件就自愈"—— 这在"上次被强杀留下污染"
     时没错，但在"我刚正常改了被测文件"时就变成了**静默回滚**（实测丢了
     一整轮测试补强，而且基线还是绿的，看不出异常）。
     修法：改用**中断哨兵**（`.in-progress`），只在"上次运行被中断"时自愈。
  2. **两个会改写源文件的夹具并行会互相污染**。修法：**共用一把文件锁**，
     拿不到锁就立刻退出并说明原因。**别把流程纪律寄托在人的记性上。**

六、什么样的改动才算"做完了"
--------------------------------------------------------------------------------

沿用本项目已经形成的标准（README 开发约定）：

  1. **断言必须落在"输出"上**：线上字节、ALSA/GPIO 句柄、发出的信号、
     走了哪个日志分支。—— "有测试"不等于"被测到"。
  2. **新测试必须配故障注入**，并且证明"把被测代码改坏它就会红"。
     在缺陷代码上不失败的测试**没有价值**。
  3. **行为不可观测的防御性代码，也要有静态规则守**，并在夹具里
     如实记入 `UNDETECTABLE` **并写明原因** —— 没有守卫的死角要看得见。
  4. **报覆盖率必须连分母一起报**，并把未覆盖行分成"不可达 / 可达未测"。
  5. **"X 不出现"的断言必须配阳性对照**，否则捕获管道坏了它照样通过。
  6. **机制必须用真实实现，别复制一份进替身**（除非确实链接不进来，
     且要在注释里说明那是副本、由哪条静态规则守）。
